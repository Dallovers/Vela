# 后续优化路线

本路线从 0.1.7 的真机结果出发，参考 DSH Go 的工程和交互思路，逐步把单次目标自动操作发展为可恢复、有上下文、能询问用户的任务助手。本文保留整体目标；0.1.8 已完成第一条会话/多任务/问答恢复纵向流程，具体已实现与未验证范围见 [会话实现](../architecture/SESSION_V0_1_8.md) 和 [验收报告](../../reports/acceptance/v0.1.8/验收报告.md)。其余条目继续作为规划。

## 产品目标

用户创建一个任务会话，在同一上下文中连续运行相关子任务。助手记住当前目标、用户约束、已经核实的结果和下一步，在遇到歧义时暂停并请用户补充，而不是猜测坐标或重复执行。用户可以检查计划、调整步骤、输入补充指令、继续、暂停或停止。

## 阶段 0：建立下一版基线

- 阅读交接说明、0.1.7 验收报告、应用源码和 DSH Go 的当前页面/架构实现。
- 保留 0.1.7 APK、哈希、设备验证结果和 32 项基线测试。
- 给当前 Compose 页面、任务执行状态、日志保留和截图目标定位补架构图及风险清单。
- 确定第一轮范围、数据结构、交互流程和验收任务，再开始改动。

## 阶段 1：任务会话与多任务上下文

让任务和上下文成为明确的本地数据模型，而非只存在于一段长提示词。

- `TaskSession` 保存会话标题、用户总体目标、用户约束、共享的事实摘要、当前子任务、最近结果和任务列表。
- 子任务有稳定 ID、状态、顺序、输入、完成条件、结果摘要及风险级别；建议覆盖待办、运行中、等待用户、暂停、完成、失败与跳过。
- 支持从当前场景继续执行相关子任务；不要每个子任务都强制回桌面。起始方式、目标 App/联系人等上下文边界由用户目标和重新观察决定。
- 每个模型请求只发送“共享摘要 + 当前任务 + 最近必要历史 + 当前屏幕观察”，避免无限增长，也避免用旧截图覆盖当前观察。
- 完成的子任务写入结构化摘要，后续相似任务能复用用户明确给出的偏好和已核对事实；不推断敏感信息，不把模型猜测记录为事实。
- 支持继续当前会话、从模板创建新会话、编辑/重排/删除尚未执行的步骤、清空上下文、删除整个会话，以及检查将要交给模型的上下文。
- 明确何时共享上下文、何时开始独立上下文；不要把不同联系人、账户或聊天任务的状态混在一起。
- 任务队列持久化，Activity 重建或进程重启后恢复为可见的暂停/待恢复状态；恢复时重新截图和识别，绝不盲目重放上次动作。
- 评估 Room 或现有轻量存储方式，给 schema 留版本迁移；API key 继续独立加密，屏幕原图按最少保留原则管理。

## 阶段 2：主动询问用户

- 给模型返回的决策定义显式类型，例如执行一个动作、向用户提问、等待确认或完成。模型的自报 confidence 分数只能作为提示，不能作为唯一安全判断。
- 在目标含糊、候选对象冲突、OCR 证据不足，或外部/不可逆动作的对象、内容和授权尚不明确时进入等待用户状态。已清楚授权的具体动作无需反复确认。
- 前台显示 Compose/Material 询问对话框：说明当前目标、已知信息、具体疑问，提供简洁选项和可编辑的自由文本/新指令输入。
- 确认/补充前暂停循环和所有手势；答复绑定当前会话和问题 ID，避免迟到回复串到其他任务。
- 用户回复后合并到会话上下文，重新获取当前截图并验证页面，再产生新动作。确认不等于跳过执行前校验。
- 助手在后台运行时，优先发送可返回 App 的通知；用户打开 App 后展示待答问题。不要依赖未授权的悬浮窗权限或系统级遮挡。
- UI 提供“继续”“修改任务”“跳过此步骤”“暂停”“结束”清晰选项。拒绝回答或超时后保持暂停，不擅自猜测。

## 阶段 3：参考 DSH Go 优化操作体验

- 逐页查看 DSH Go Flutter 前端（`app/lib/`）与 Android 原生桥接，重点理解任务/会话入口、设置和 provider 配置、页面切换、状态呈现、工具反馈与确认交互；本工程继续使用 Kotlin/Compose。参考索引见 [DSH_PRODUCT_REFERENCE.md](../architecture/DSH_PRODUCT_REFERENCE.md)。
- 根据当前工程重新设计信息架构：任务/会话列表、当前执行详情、子任务步骤、屏幕观察、待回答问题、运行记录和模型设置。
- 页面以任务状态和下一项操作为中心；显示运行、等待用户、暂停、完成和失败状态、当前步骤及最近证据。
- 将配置和频繁运行操作分开。允许用户查看、编辑上下文和行动计划，不让模型输出直接替代用户的原任务。
- 处理中文长文本、键盘弹出、小屏设备、系统栏、安全区域、旋转和字体缩放；用真机截图检查，不仅看 Compose Preview。
- 优先复用现有 Compose Material3 和本地主题，避免无理由改用其他 UI 框架。
- DSH Go 使用 AGPL-3.0。只借鉴公开可见的产品结构和交互概念；不复制源代码、图标、文案或资源。若未来提出复用其源码，先单独评估许可证兼容性。

## 阶段 4：可靠性、安全和比赛演示

- 建立有限状态机和不变量：同一时刻最多一个活动任务；停止即废弃旧 generation；每个动作只派发一次；屏幕变化后重取观察；等待用户期间绝不操作。
- 对模型超时、格式错误、服务断连、Activity 旋转/销毁、进程重启和系统弹窗做单元或集成验证。
- 对日志、上下文、截图、用户输入和密钥分别做隐私审查，默认不输出原始模型 prompt、聊天内容、输入文字或密钥。
- 以本地定位练习作为可重复无副作用的主要验收，再用设置页、微信搜索等限定任务验证；不在无人监控的条件下测试发消息或拨电话。
- 记录每个测试的设备/OS、版本、输入目标、步骤数、是否向用户询问、是否正确暂停、是否完成和失败原因。用多轮样本报告成功率，不用一次成功声称稳定。
- 准备比赛演示脚本、架构示意图、数据流和隐私说明、限制与后续路线。演示失败要有本地预录结果或截图，但须标明是录制材料。

## 推荐第一阶段交付

先做一条完整纵向流程：创建会话 → 查看和修改 2 到 3 个子任务 → 执行本地练习任务 → 在歧义注入场景弹出自由文本问题 → 用户补充 → 重新观察并完成 → 查看历史摘要 → 重启后显示会话已暂停且不重放动作。

通过这条流程验证模型协议、任务状态机、数据存储、询问交互和页面导航，再扩展其他 App。每阶段结束更新 [验收报告](../../reports/acceptance/README.md) 和 [比赛材料](../presentation)。
